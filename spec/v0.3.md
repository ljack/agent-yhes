# Realtime broker notifications, v0.3

Status: experimental implementation, 2026-11-13. Jarkko requested a realtime
message broker and delegated the broker choice. This profile uses NATS JetStream
and builds on the [remote Git profile](v0.2.md). The [server and usage guide](../docs/BROKER.md)
contains runnable configuration and links to the broker's own specifications.

The security-capable v0.3 draft adds the [signed event format](secure-events.md)
and [secure core](../secure/README.md). Those components are implemented and tested
separately; this broker helper still uses the earlier trusted-participant records.
The integration and historical-membership acceptance gates remain open before
the v0.3 security release.

## 1. Responsibilities

Git stores the shared tickets, messages, sessions, receipts and operation results.
NATS distributes durable change notifications so active receivers can fetch the
new records promptly. A claim is still arbitrated and confirmed by Git. The
broker needs no Git credential and carries no message bodies or ticket contents.

This version reduces the wait between Git publication and receiver discovery.
Publication itself still waits for Git. Direct broker-first task state, chat
payloads that bypass Git, automatic model invocation and vendor-specific wake-up
are outside this profile. A listener emits JSON that an active harness or a
separate authorized adapter can consume.

Git records retain version `0.2`; the notification envelope uses `0.3`. Existing
v0.2 writers continue to work. Their changes appear at the next reconciliation
unless that writer subsequently uses `flush` to notify the broker.

## 2. Server and channel identity

Use NATS Server with JetStream enabled. The reference implementation was tested
with NATS Server **2.15.3** and **nats-py 2.16.0**. v0.3 adds this optional Python
dependency; local v0.1 and Git-only v0.2 retain their standard-library runtime.

Let `H` be lowercase SHA-256 of the v0.2 reference JSON encoding of
`[project_id, full_coordination_ref]`. The project ID comes from the validated
Git descriptor, and the ref comes from the user's selected channel.

| Item | Value |
| --- | --- |
| NATS subject | `yhes.v03.<H>.changed` |
| Stream | `YHES_V03_<first 24 characters of H>` |
| Durable consumer | `YHES_<first 32 characters of SHA-256(encode([H, node, session]))>` |
| Publish deduplication ID | `<H>:<operation_id>` in the `Nats-Msg-Id` header |

Equivalent HTTPS/SSH Git remote URLs reach the same subject when they reference
the same project and branch. Each local node/session has a separate consumer;
listeners are broadcast recipients, not members of a shared worker queue. A
local listener lock prevents two processes sharing one session's consumer.

`broker-init` creates the stream explicitly. Reference defaults: file storage,
limits retention, one replica, 24-hour retention, 10,000 hints, 8 MiB total,
4 KiB per hint, 120-second publish-deduplication window, 128 consumers.
An existing stream must match the exact subject, file storage and limits
retention; the command leaves operator-defined limits unchanged. Production
replication and resource sizing are operator choices.

## 3. Notification envelope

One UTF-8 JSON object, at most 4 KiB, with exactly these fields:

```json
{
  "protocol": "local-agent-cooperation.realtime",
  "version": "0.3",
  "type": "channel.changed",
  "project": "p_00000000-0000-4000-8000-000000000001",
  "ref": "refs/heads/agent-yhes/state",
  "operation_id": "o_00000000-0000-4000-8000-000000000002"
}
```

Unknown fields, duplicate keys, oversized records, invalid IDs and a different
project/ref are rejected. The receiver never treats the operation ID as a command
to execute or a claim to trust. Even a valid hint only prompts a read of the
receiver's already configured Git remote. No broker-supplied URL, path, message
body, user instruction or approval is accepted.

## 4. Publishing and the notification outbox

`tools/realtime.py` accepts the v0.2 commands. It first completes the ordinary
Git operation and verifies the operation receipt on the remote. Only afterward
does it publish the change hint and wait for the JetStream storage acknowledgment.

The v0.2 local pending records already retain confirmed operation IDs. They form
the durable source for the notification outbox. A local marker is written under
`<git-dir>/agent-yhes/<channel>/notifications/<broker-key>/<operation>.json`
after broker acknowledgment. The marker contains the stream sequence and whether
the server identified a duplicate. Tokens and message bodies are absent.

A successful Git result gains `realtime: {state: "stored", notifications,
remaining}`. Broker failure returns the same confirmed Git result with
`realtime: {state: "pending", reason}`. It does not turn an accepted claim into
a failed claim. `flush` later republishes confirmed operations lacking a marker.
The just-completed operation is prioritized; a bounded flush handles the backlog.

After a lost publish acknowledgment or a crash before writing the marker, the
same message ID is reused. JetStream deduplicates within its configured window.
Later duplicates remain safe: a hint causes a fresh read, not a repeated action.
If the producer crashes before its local confirmed state was saved, v0.2
`resolve`/`resume` restores it from Git and the next flush can publish the hint.
The listener's periodic reconciliation covers any remaining notification gap.

## 5. Listening, replay and missed notifications

`listen --session SESSION --seconds 30` performs these steps:

1. Fetch and validate Git state, verify that the session belongs to this local
   node, and emit an initial inbox snapshot.
2. Connect to the broker and bind a durable pull consumer for the channel.
   Delivery starts with retained hints and uses explicit acknowledgments.
3. Read up to 16 hints per batch. Validate each hint. For a valid batch, fetch
   the current Git inbox once, emit it if the observed commit changed, and only
   then acknowledge the valid hints. The Git read uses the receiver's credentials.
4. On a Git outage, leave valid hints pending for redelivery. On a broker outage,
   reconnect with a bounded backoff while continuing Git reconciliation.
5. Reconcile against Git periodically, by default every 30 seconds, even when
   no hint arrives. This covers older writers, expired hints, a lost broker store,
   or a producer that stopped before publishing. Startup always performs this read.

The broker acknowledgment timeout is 30 seconds. Each consumer permits at most
64 pending acknowledgments. Batches are coalesced and Git refreshes are paced
to avoid one fetch per incoming hint. Invalid hints are terminally acknowledged
and counted; they produce no inbox payload or project operation.

The reference listener runs for a bounded positive interval up to 300 seconds (fractional
seconds are accepted for tests). An adapter can invoke it again. It emits
`channel.changed` snapshots with `reason: startup|broker|reconcile`, session,
observed Git commit and inbox records. Each output line is a complete JSON object,
including the final `listen.finished` delivery/error counters.
Consumers can fetch `tickets` after a channel change to discover new work.

If output fails before acknowledgment, the hint remains eligible for redelivery.
If the process stops after output but before acknowledgment, duplicate snapshots
are possible. Use record IDs and the ordinary v0.2 workflow to avoid duplicate
side effects. Expiry and ownership are checked in Git before new work.

## 6. Delivery and authority remain separate

| Signal | Meaning |
| --- | --- |
| Git `delivery: confirmed` | The operation exists in the authoritative channel. |
| Realtime `state: stored` | The broker acknowledged notification storage. |
| Broker consumer acknowledgment | This listener refreshed Git and emitted any changed snapshot. |
| Project `seen` / `handled` receipt | The participant explicitly recorded that application-level action in Git. |

A listener never writes `seen` or `handled` automatically. Broker credentials
control notification access; Git credentials control the records. Neither a
notification nor a human-labelled session grants new user authority to an agent.
All fetched message bodies remain attributed peer data.

## 7. Connection and deployment profile

The user configures `YHES_BROKER_URL`, `YHES_BROKER_TOKEN`, and optionally
`YHES_BROKER_CA`. Credentials are environment/configuration data and are excluded
from protocol files and URLs. Remote connections require `tls://` with normal
certificate and hostname verification. Plain `nats://` is accepted only for
literal loopback addresses or `localhost`.

The supplied configuration is for one trusted project group per server/account,
with token authentication. For separate groups on one server, use NATS accounts
and subject/API permissions; Git permissions alone do not configure those broker
boundaries. The v0.3 client does not automatically enroll users or issue credentials.

The initial server is a single persistent JetStream instance. Protect its data
directory, back it up as appropriate, and choose replication through NATS server
configuration when needed. If the broker loses its history, Git reconciliation
still discovers retained project records. Realtime access exposes opaque project
and operation IDs and activity timing, even though hint bodies contain no prose.
