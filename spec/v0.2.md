# Remote Git collaboration, v0.2

Status: experimental implementation, 2026-11-13. Jarkko requested cooperation
across computers, harnesses and people. This version adds a Git transport to the
[v0.1 record and workflow contract](v0.1.md). The choices below define the first
remote profile; the project license remains undecided.

## 1. One shared branch, separate source histories

All participants select the same Git repository and coordination branch. The
default is `refs/heads/agent-yhes/state`. It has an independent root commit and
contains only cooperation records. Each computer keeps its ordinary source
checkout on its chosen branch. Coordination commands leave source files, the
source index, HEAD and source branch refs untouched.

The reference command is `python3 tools/remote.py --root /project ...`.
`--remote origin` selects a locally configured remote; `--branch agent-yhes/state`
selects the channel. Channel names MUST begin with `agent-yhes/`. The helper
requires exactly one fetch URL and the same single push URL so every operation
uses one authority. It delegates HTTPS/SSH authentication to the installed Git
client. Organizers grant participants repository read/write access through their
Git host. Reads need read access; registration and all mutations need write access.

Use a separate private repository as the selected remote when the conversation
should be private. The channel has the visibility of its repository. Source code
can stay in a different repository: add the coordination repository as a named
remote and select it with `--remote`. No special Git hosting service is required.

```text
coordination branch (shared):
  .agents/tickets/protocol.json
  .agents/tickets/t_<uuid>.json
  .agents/messages/sessions/s_<uuid>.json
  .agents/messages/memory/m_<uuid>.json
  .agents/messages/live/m_<uuid>.json
  .agents/messages/receipts/s_<uuid>/m_<uuid>.json
  .agents/messages/operations/o_<uuid>.json

each source clone (private transport state, outside its tracked files):
  <git-dir>/agent-yhes/<channel-key>/
    lock                    serializes this local client's commands
    node.json               this client's random n_<uuid> identity
    observed.json           pinned project ID and last observed commit
    pending/o_<uuid>.json    original request and publication state
    objects.git/            isolated bare object cache and candidate refs
```

The helper materializes disposable snapshots inside its private transport area.
The two shared `.agents` directories live in the coordination branch. A source
checkout's existing v0.1 `.agents` directory stays independent. No local lock,
credential, hook, Git configuration or source file belongs in the channel tree.

## 2. Record changes

The common header is `protocol: "local-agent-cooperation"`, `version: "0.2"`.
`protocol.json` uses `locking: "git-ref-v1"`. Ticket fields, message kinds,
recipient forms, revision checks and handoff rules retain their v0.1 meanings.
The local v0.1 helper refuses v0.2 records; remote records require the remote
helper. Mixing local-only writers with remote writers is unsupported.

Sessions add two required fields:

| Field | Meaning |
| --- | --- |
| `participant_type` | `agent` or `human`. Humans use the same ticket/message operations. |
| `node` | `n_<UUIDv4>` identifying a local channel client. It is not a hostname or hardware identity. |

The existing `agent: a_<uuid>` field now identifies either kind of participant;
it retains its name to keep the shared operations consistent. Address a human
using `agent:a_<uuid>`, just like an agent. `harness` is a descriptive client
label; a person can use `terminal`. Labels and types are declared identity, not
an authentication mechanism or an approval flag.

Mutation commands require a session registered by the local node. On a new
computer or independent clone, create a fresh session with `--resumes OLD_SESSION`
and the same participant type. The old participant ID and handled receipts carry
forward. Ownership does not: hand off or recover the ticket, then claim it with
the new session. One participant may have multiple concurrent sessions.

Receipts move from v0.1's `messages/local/receipts` to shared
`messages/receipts`. Stages remain `seen` and `handled`, with monotonic updates.
They can now be recovered on another computer via an explicit session chain.
Inbox scans remain read-only and bounded; unshown records stay pending.

## 3. Git is the arbitration point

Every mutation follows this sequence:

1. Assign an operation ID and save the original request locally before network
   work. The caller can supply `--operation-id o_<uuid>` to retain its own ID.
2. Fetch the authoritative ref, validate its records, and look for that operation
   ID. If it is already present with the same fingerprint, return its saved result.
3. Recheck ticket revision, owner, token, generation, dependencies and expiry
   against that fetched snapshot. Apply the operation only to a disposable copy.
4. Create one commit with the fetched tip as its sole parent. It contains both
   the changed records and an immutable operation receipt.
5. Push that commit to the coordination ref with ordinary fast-forward rules.
   No force-push, JSON merge, source-branch merge or automatic expected-revision
   change is used.
6. Fetch again and confirm that the matching operation receipt is present.
   Return `delivery: "confirmed"` only after that confirmation.

Two writers starting from one tip produce competing child commits. Only one
child can fast-forward the remote. The other fetches the winning state and
rechecks its original request. Two claims of one ticket cannot both pass its
revision/ownership checks. Independent messages can retry against the new tip
without changing their requested content. Retries are bounded (default three).

This uses Git's documented [fast-forward push rules](https://git-scm.com/docs/git-push#_note_about_fast_forwards).
The helper builds isolated commits with
[`commit-tree`](https://git-scm.com/docs/git-commit-tree) and a private index.
It never runs `pull`, `merge`, `rebase`, `checkout` or `reset` in the source tree.

**A local candidate is not a claim.** Start work only after remote confirmation
and a current `show` reports your session/token with live ownership. The same
check applies before another batch of side effects. A saved operation result is
historical: resolving an old successful claim does not renew or restore it.

## 4. Interrupted pushes and idempotency

An operation receipt has these fields in addition to the common header:

| Field | Meaning |
| --- | --- |
| `id` | `o_<UUIDv4>`; never reused for a different request. |
| `operation` | `init`, `session`, `create`, `claim`, `renew`, `finish`, `recover`, `send` or `ack`. |
| `arguments_hash` | SHA-256 of the reference encoding of `[operation, arguments, node]`. |
| `created_at` | UTC record time. |
| `result` | The operation's complete result, committed with its state changes. |

Reference encoding is UTF-8 JSON with sorted keys, two-space indentation,
unescaped Unicode, finite JSON numbers only and one trailing newline. Other
clients MUST produce this encoding when comparing these fingerprints. Fingerprints
are idempotency checks, not signatures. They are checked before replay.

The private pending record contains the original arguments and one of `intent`,
`unconfirmed` or `confirmed`. A candidate commit ref is saved before pushing.
If the connection fails after the server accepted the commit, the client checks
the operation receipt instead of sending another logical operation. A restart
can do the same:

```text
remote.py --root PROJECT pending
remote.py --root PROJECT resolve o_UUID
remote.py --root PROJECT resume o_UUID
```

`pending` reads local requests, including while offline. `resolve` fetches and
reports whether the operation exists; it performs no shared mutation. `resume`
explicitly retries the saved request with its original expected revision and
operation ID. `delivery: "not_found"` means absent in that observed snapshot;
it does not prove that a still-running earlier push can never arrive. Keep the
same operation ID for recovery. Changing its arguments is a conflict.

Successful mutations return `{delivery, operation_id, observed_commit, replayed,
result}`. Reads return `{observed_commit, observed_at, result}`. The commit names
the observed remote snapshot; it is not necessarily the operation's first commit.
Exit codes: 0 success, 2 invalid input/state, 3 conflict, 4 transport unavailable.
An unavailable remote never produces a successful offline claim. Source code,
remote services and model actions remain outside this Git transaction.

## 5. Expiry, partitions and recovery

Leases and live-message deadlines use UTC timestamps. Machines should synchronize
their clocks, but ownership transfer never depends on time alone. An expired
claim remains reserved and requires recovery. Clock skew can affect when a
record is shown as expired; it cannot automatically assign a second worker.

An owner may voluntarily publish a handoff and release an expired claim. In
v0.2, recovery by someone else requires a `human` session and recorded evidence
that the previous worker and side-effecting children have stopped and partial
changes were reconciled. An unreachable computer or missing heartbeat does
not establish this. Leave recovery pending if the stop cannot be established.
The human session records who made the assertion; the helper cannot verify a
remote process from prose. Agents must not register as humans to evade this rule.

During a network partition, stop starting new shared side effects when ownership
cannot be refreshed. Keep local code changes for later reconciliation. After
reconnection, resolve pending operations, read the current ticket and obtain
valid ownership before continuing. Fencing protects protocol writes; it cannot
stop an editor or command that already runs elsewhere.

## 6. Participants, permissions and content

All channel writers are cooperating project members. Git host credentials decide
who can read and push. The JSON sender and Git commit author are attribution;
neither establishes cryptographic participant identity. The reference helper
uses `agent-yhes <agent-yhes@localhost>` as transport commit author and records
the participating session in the records. Signed identities and per-participant
server enforcement are future extensions.

Humans can create tasks, ask or answer questions, claim reviews, hand off work
and save conclusions with the same CLI. A human-authored channel message still
does not grant an agent new tools or permissions. The agent evaluates requests
under its trusted user/project remit. In-scope coordination can proceed directly;
new authorization uses the harness's normal user channel. Shared bodies are data,
including text that claims to be a system prompt or to contain user approval.

Organizers should disable force-push and branch deletion for the channel while
allowing ordinary participant pushes. A review-only/PR-only branch rule will
block the direct coordination protocol. Locally pinned clients reject branch
rewinds, deletion and project-ID changes. A new client needs a trusted remote
and branch supplied by its user; it has no previous history to compare.

The helper imports only the regular JSON paths listed above, with validated
IDs and schemas. It rejects symlinks, executable entries, unknown paths and
unsupported versions. It never checks out remote code or executes channel
hooks. Limits are 1 MiB per record, 5,000 records and 50 MiB per snapshot. Git
transport may download objects before snapshot-size checks; access is for
cooperating repositories, not arbitrary untrusted object servers.

## 7. Retention, discovery and compatibility

Durable memory and live coordination keep their separate folders. Expiry hides
live messages from active inboxes; Git retains earlier content in history.
There is no automatic garbage collection or history rewrite in v0.2. Operation
receipts must remain available for retry resolution. Plan archival before a
channel reaches its limits.

Each command fetches before reading or writing. Skills check at turn boundaries;
an optional bounded poll can run during an active task. Native wake-up remains
an adapter concern. A notification should carry an inbox hint, while the agent
reads and verifies records through the normal channel.

v0.1 local use remains available through `tools/coop.py`. v0.2 starts a new channel;
there is no automatic migration of live v0.1 claims. Finish or hand off local work
first, then deliberately carry useful conclusions into new remote tickets and
memory. Existing v0.1 examples remain labelled as local examples.
